# 當沖訊號系統 v1（永豐 Shioaji）

**定位：AI 給訊號、你手動下單。** 系統不碰下單 API，也不預測方向。
它只做三件事：盤前收斂標的、盤中依硬規則發訊號、盤後做紀律稽核。

---

## 為什麼盤中不放 AI

LLM 在 tick 級別沒有優勢：延遲、噪音、無法驗證推理、樣本外失效。
把模型放在進場決策上，你會得到一個講得頭頭是道但無法歸因的黑盒子。

所以分工是：

| 層 | 誰負責 | 為什麼 |
|----|--------|--------|
| 盤前選股 | 規則 + 你的判斷 | 收斂到 5 檔，AI 只幫忙整理題材 |
| 盤中觸發 | **寫死的規則** | 要快、要可重現、要事後能歸因 |
| 風控閘門 | **寫死的規則** | 要比你的手快 |
| 盤後覆盤 | **AI 最強的一層** | 找出你重複犯的錯 |

## 安裝

```bash
pip install -r requirements.txt   # shioaji 1.7.x + requests
cp .env.template .env             # 填入金鑰
```

Shioaji 官方支援 Python 3.7~3.14；本專案的 CI 測 3.10 / 3.11 / 3.12。

**Windows 使用者**：繁中環境的主控台預設是 cp950，印不出 ✅⚠️❌ 這類符號。
程式會自動退回 `[ OK ]` / `[WARN]` / `[FAIL]` 純文字標記，中文一律正常顯示，
不會當掉。想看原本的圖示就先切 UTF-8：

```cmd
chcp 65001
set PYTHONUTF8=1
```

`requests` 只有 Telegram 推播用得到，缺席時訊號照樣印在畫面上；但如果你已經
設好金鑰卻沒裝它，`notify()` 會用 ERROR 級別吵你 —— 「訊號發不出去」不能安靜地發生。

`.env`（`config.py` 啟動時會自動讀，不需要 source；已存在的環境變數優先）：

```
SHIOAJI_API_KEY=xxx
SHIOAJI_SECRET_KEY=xxx
SHIOAJI_SIMULATION=1       # 前三個月不要改成 0
TELEGRAM_BOT_TOKEN=xxx     # Line Notify 已停止服務，改 Telegram
TELEGRAM_CHAT_ID=xxx

# 只有真錢模式需要（見下方「電子憑證」）
SHIOAJI_CA_PATH=
SHIOAJI_CA_PASSWD=
SHIOAJI_PERSON_ID=
```

金鑰在永豐官網申請，需先簽署 API 服務條款與風險預告書。
**Secret Key 建立後只會顯示一次**，當下沒存就只能重新申請一把。

### 電子憑證

帳務查詢需要電子憑證（從永豐電腦版下單軟體 e-Leader 下載的 `.pfx`）。
本系統不下單，但**風控的日虧上限與連敗停手都建立在帳務查詢上** ——
真錢模式沒有憑證就查不到損益，閘門會在第一個訊號直接關閘停手。

`broker.login()` 會在真錢模式自動啟用憑證，被拒就當場拋出例外。
寧可在登入時炸開，也不要等到盤中才發現整套風控沒有作用。
模擬模式不需要憑證。

### 裝完先跑這三個

```bash
python3 test_daytrade.py   # 329 項離線測試，不需金鑰與網路
python3 dryrun.py          # 灌模擬 tick 跑一整天，驗證管線沒斷
python3 preflight.py       # 連線體檢：核對 Shioaji 回傳格式（需金鑰，只讀不下單）
```

Windows 的命令是 `python`，沒有 `python3`（打了會說「不是內部或外部命令」）。

`preflight.py` 是**上線前的守門人**。整套系統對 Shioaji 的回傳格式做了一堆假設
（欄位叫什麼、`day_trade` 是什麼值、分鐘 K 的 `ts` 是起點還是終點、損益查不查得到），
而那些假設錯了**盤中不會報錯** —— 你只會得到一個整天沉默、或安靜地用錯誤水位
算停損的系統。它逐項印出實際看到的值讓你核對，有 ❌ 就以 exit code 1 結束。

**切換 `SIMULATION=0` 之前一定要跑一次**，特別是「已實現損益」那一項：
查不到的話風控會直接關閘停手（見下方「風控的煞車」）。

`dryrun.py` 驗的是**管線**不是策略：訊號條件、風控閘門、覆盤版型有沒有真的串起來。
每次改完 `config.py` 都跑一次，免得在真正的 09:00 才發現整天不會發訊號。
它產出 `journal/DRYRUN-YYYYMMDD.md`，不會蓋掉真實日誌。

## 每日流程

| 時間 | 動作 |
|------|------|
| 首次／改 SIMULATION | `python preflight.py` → 連線體檢 |
| 08:40 | `morning.bat`（排程）→ 選出**量比前 10 檔**，盤中只盯這 10 檔（v10，`SCREEN["watch_top"]`；一天最多 3 個訊號不變）；名單正常就不推播，只有失敗或 0 檔才推（使用者 10-08）。08:50 監看啟動的「✅ 今日監看 10 檔」會列出是哪 10 檔 |
| 08:45 | 想自己挑再跑 `--top N` 砍監看範圍，或直接編輯 `watchlist.json` 的 `items` |
| 09:00 | `python signals.py` → 開始監看，訊號推 Telegram |
| 13:30 | 自動收工 |
| 14:00 | `afternoon.bat`（排程）→ 回推結局、寫 `journal/YYYYMMDD.md`、推日報 |
| 每週日 | 把整個 `journal/` 丟給 Claude 做跨日稽核 |

**休市日（10-09 起）。** 排程是週一到週五每天跑，它不知道哪天休市 —— 10-09 國慶
補假照樣「✅ 今日監看 10 檔」、09:30「今日訊號 0 個」。現在三支程式一開始先查
`market_calendar.py`（證交所公告的 2026 休市日）：

- 08:40 選股：不跑、不寫名單、不推播
- 08:50 監看：推一行「📅 今天 10-09（五） 休市（國慶日補假），不監看、不出日報。
  下一個開盤日：10-12（一）」就結束，不碰 `state.json`
- 14:00 日報：不出

表上沒有的休市日（颱風假、臨時公告）：監看 09:03 還沒收到任何一筆成交，就查
0050 今天有沒有任何一根分鐘 K —— 沒有就推同一行「休市」、提早收工，日報也不出；
有 K 棒卻收不到成交，推「⚠️ 監看可能收不到行情」（那是故障，不是休市）。查詢本身
失敗時不當休市。

「✅ 今日監看 10 檔」只代表**登入永豐、訂閱完成**，不代表收得到報價 —— 訊息上現在
寫明「09:03 確認有沒有收到行情」。09:30 那一則也分清楚：一筆成交都沒收到時寫
「不是沒有突破，是根本沒有行情」，不再說成「沒有一檔通過突破、均價線、量能」；
有行情時寫「收到成交 N 檔、開盤區間定好 N 檔」（10-09 使用者：「真的有連線永豐
嗎？如有連線，應當回報無法監看啊」）。

**每年要補一次表**：證交所年底公告下一年的休市日，補進 `market_calendar.py`。
12 月起表上還沒有下一年時，08:50 的監看會多推一行提醒。

### 讓 Windows 自己在 08:40 跑

`morning.bat` 就是為這件事準備的（跑的是 `python screener.py --push --alert-only`）。
註冊成排程，平日 08:40 自動執行：

```
schtasks /create /tn "盤前選股" /tr "\"%CD%\morning.bat\"" /sc weekly /d MON,TUE,WED,THU,FRI /st 08:40 /f
```

（在 `daytrade-signals` 資料夾裡執行。要取消：`schtasks /delete /tn "盤前選股" /f`）

**前提：電腦那個時間要是開機且未睡眠的狀態。** 筆電闔上蓋子排程不會跑 ——
真要每天穩定執行，得讓它保持喚醒，或改放在一直開著的機器上。

**08:40 不會再收到「今日觀察名單」。** 使用者 10-08：「這訊號不用給」。名單照樣
寫進 `watchlist.json` 給盤中監看用，只是不推。會推的只剩真的要人知道的兩種：
選股失敗（附錯誤訊息），或名單是 0 檔（今天什麼都不會監看）。
想看名單就打開 `logs\morning.log`（整張表都印在裡面）。**不要為了看名單在盤中重跑
screener.py** —— 它會覆蓋當天的名單存檔，事後 `whynot.py` 對的就不是盤中監看的那一份。

**每天確認系統有在跑，改看 09:30 那一則「🔒 進場窗口已關閉」。** 它一定會發，
0 個訊號的日子也發。09:31 還沒收到，代表出事了：電腦睡著了、排程沒跑、或程式
當掉了 —— 照下面的方法查 `logs\morning.log` 和 `logs\monitor.log`。

排在 08:40 的那一次沒有人在看畫面，所以 `morning.bat` 會把每次執行的完整輸出
附加到 `logs/morning.log`（含結束碼）。事後要查當天到底發生什麼事就看這個檔案：

```
schtasks /query /tn "盤前選股" /v /fo list      查排程本身：上次執行時間與結果
type logs\morning.log                           查程式跑出了什麼
morning.bat                                      手動補跑一次（畫面會印出最後 25 行）
```

> **v10 起只盯量比前 10 檔。** 使用者 10-08 先說「盤前選出三檔，就盯這三檔」，
> 同一晚知道只盯 3 檔多數日子會是 0 訊號，改成 10 檔。一天最多 3 個訊號不變 ——
> 盯得多只是機會多，不會做得多。沒被選上的那幾檔照樣存進當日存檔（`not_watched`），
> 事後查得到「是不是漏掉了好的」。
>
> **（v9 以前）驗證期：不要用 `--top`，監看完整候選池。**
>
> 兩個理由：
>
> 1. **可重現。** 手挑的名單每天標準都不一樣，20 天之後賺賠都無法歸因 ——
>    不知道該記在規則頭上還是那天的判斷頭上，等於白跑。
> 2. **樣本數。** 訊號要同時滿足突破、帶量、站上均價三個條件，多數日子是 0 個。
>    只監看 5 檔的話，20 天可能只累積到十幾個樣本，算不出可信的勝率。
>    風控閘門本來就擋在「一天最多 5 個訊號」，**監看 20 檔不會讓你多做任何一筆**，
>    只是讓有機會觸發的標的多 4 倍。
>
> 推播仍然只列前 5 檔（`--push-top`，純顯示），但訊息會寫明實際監看幾檔。
> 等你確認規則本身站得住，再加回自己的判斷。

### 收盤後的日報 —— 自動推到手機

`review.py` 跑完會把當日結果推一則到 Telegram：今天幾勝幾敗、每一筆的結局與 R
倍數，加上讀 `outcomes.csv` 算出來的**累計**勝率與賺賠比。細節仍在 journal 裡，
這則訊息只負責讓你兩秒看完結論。

每一筆都帶金額（依訊號的建議張數與目前成本設定估算）。金額先各自四捨五入再加總，
**合計一定等於上面各筆相加** —— 差一塊錢會讓人開始懷疑哪個數字才是對的。

訊號數上限是 5 但一天只准做 4 筆，所以訊號超過 4 個時會另外標出「照上限只做前 4 筆」
的金額。把 5 筆的總和講成今天會賺到的錢是高估，而那第 5 筆照規則根本不會下單。

零訊號的日子會明講「這是正常的一天」，沒回推成功的日子也會說清楚是哪一種 ——
三種情況三句話，不會混在一起。

預設會推。同一天重跑覆盤時加 `--no-push` 就不會重複推播：

```
python review.py --no-push
```

推播失敗不會讓覆盤失敗 —— journal 在推播之前就寫好了。

### 訊號發出之後 —— 盤中即時追蹤

訊號發出後，`signals.py` 會繼續盯著那一檔的報價，**碰到停損或目標的當下就推播**，
13:25 還沒走完的：當沖規則（v5 以前）以最後報價平倉並告知；v6 起改成留倉過夜（見下）。

### 留倉與續抱：訊息只講事實，決定由你

使用者 10-07：「沒碰停損自己決定要不要留倉，因為你沒把握明天留倉會漲」。所以訊號、🔒、
13:25、✅ 這幾則都不寫「要留到明天」「停損上移」「跳空會賠更多」這類勸說，只寫價格、
漲停、還沒結束這些事實，最後一句是「由你決定」。系統照樣把還沒結束的追蹤到隔天 13:25，
那是為了 20 天後回答得了「留倉划不划算」，不是建議你留。

### v10：六條出場，回到當沖（10-08 起，10-12 第一天）

使用者 10-08 貼了一篇當沖出場的六個條件，選「直接改成新規則」。四個數字也是
使用者選的。進場規則照 v9 不變；出場由 `exits.py` 判斷，盤中（看 tick）和收盤
回推（看分鐘 K）共用同一份程式，兩邊才對得起來。

| 條件 | 怎麼判 | 推播 |
|---|---|---|
| 1. 進場理由消失 | 跌回區間高點下方 0.2%，或跌破均價線下方 0.2%。**那一分鐘收盤在線下才算**，出場價 = 那一分鐘的收盤 | 🚪 |
| 2. 虧損到設定金額 | 硬停損。單筆 4,000 元，張數照這個反推 | 🛑 |
| 3. 到目標先出一半 | 漲到「目標距離的一半」先賣一半張數；剩下的從最高點回落 1.5% 出，不低於成本。只有 1 張分不了 → 整張改移動停利 | 🟡 先出一半、💰 移動停利 |
| 4. 跌破當日關鍵價 | 跌破當日開盤價（進場前就定好，寫在訊號上）。同樣**那一分鐘收盤在下面才算** | 🚪 |
| 5. 量能萎縮 | 基準 = 進場後前 10 分鐘的量。進場 20 分鐘後，最近 10 分鐘的量不到基準的一半，**而且**這 10 分鐘價格上下不到 1% | 💤 |
| 6. 時間到 | 13:25 全部平倉，不留倉（v6 的「抱兩天」取消） | ⏹ |

- 一碰就算的：停損、先出一半、移動停利。一分鐘收盤才算的：開盤價、跌回區間、均價線
  （10-08 晚改：開盤後半小時上下震盪，單一筆擦過去就出的話，跳空開高的股票幾乎
  每一筆都會被洗掉）。訊號那一刻所在的那一分鐘不判，從下一個完整的一分鐘開始。
- 量縮的基準原本是「進場前每分鐘平均量」，裡面有開盤爆量、基準偏高，10-08 晚改成
  進場後前 10 分鐘。
- 同一分鐘裡好幾條都成立：停損 → 先出一半 → 移動停利 → 開盤價 → 跌回區間 → 均價線 → 量縮。
- 出場價記的是「跌破那條線之後第一個成交得到的合法檔位」（100 元以上一檔 0.5），
  不是那條線本身 —— 線不一定是一個買賣得到的價格。
- 買入訊號上會列出每一條的價位（「出場（哪一條先到就出）」那一段）。訊息是精簡版
  （使用者 10-08：「後面的括號說明需要嗎？」→ 精簡；同晚再拿掉追高 %、開盤離昨收 %、
  最多賠多少三個括號，數字照記在 `outcomes.csv`）。「收盤才算」的三條（開盤價、跌回
  區間、均價線）放在最後，自己一個小標題「那一分鐘收盤在線下才出：」。
  「目標」那一行不印 —— v10 不會在目標價賣，目標只拿來算「先出一半」的價位。
- 先出過一半的那一筆，日報與 `outcomes.csv` 的報酬、R 是兩段照張數合起來算的；
  `half_exit` 欄記先出一半的價位，`result` 記剩下那一段的出場原因。
- 收盤回推用分鐘 K 近似：均價線用 (高+低+收)/3 × 量 累計（kbars 沒有成交金額），
  同一根 K 先碰到「先出一半」的，那一根不再判移動停利。盤中 tick 判定過的一律以 tick 為準。
- `config.py` 的 `exit_rules` 設成 `False` 就退回舊的「停損／目標／13:25」。

### 開盤前試撮方向：只記錄，不當條件（10-08 起）

使用者 10-08 貼了一篇「試撮價持續往上墊高 = 買方開盤前就傾斜」，選**只記錄**：

- 盤中監看 08:50 開，收得到的是 08:5x～09:00 的試撮報價（最後那十分鐘，
  文章說的「最後幾秒抽單」也在裡面）。09:00 以後的試撮（13:25～13:30 收盤
  集合競價）不算。
- 試撮報價**不碰**開盤區間、均價線、量能、出場判斷 —— 只記第一筆、最後一筆、
  往上跳幾次、往下跳幾次。
- 訊號照發，訊息上不出現（不加讓你自己判斷的指標）。
- 記進 `outcomes.csv` 與 `candidates.csv`：`sim_from`（第一筆試撮的時間）、
  `sim_move_pct`（第一筆到最後一筆走了幾 %）、`sim_ups`、`sim_downs`。空白 =
  沒收到試撮（不知道），不是「沒動」。舊的 `candidates.csv` 第一次寫入時會先
  換成新表頭，舊列的新欄位留空。
- 20 天後看 `python analyse.py` 第九節「開盤前試撮往哪走」：往上那一組的區間
  要明顯高過往下那一組、而且不重疊，才有理由變成條件 —— 那時才算改規則。

不改規則，所以 v10 的 20 天不用重算。

使用者 10-09 貼了一篇「盤前先刪弱股：日線 RSI 低於 50 直接跳過」，選**只記錄

### v9：開盤或回落要在昨收附近（v10 已取消，下面留作紀錄）

使用者 10-08：「開盤回落前日收盤價或開盤近前日收盤價有往上的判斷，再出訊號」。
v9 在突破、均價線、量能之外多一道條件，**下面兩個有一個成立**才發：

1. **開盤價**在昨收 ±1% 以內 —— 沒有大跳空
2. **發訊號前的當日最低點**在昨收 ±1% 以內 —— 開高之後曾回到昨收附近

「往上」不另外判，開盤區間突破本身就是往上。± 範圍在 `config.py` 的
`near_prev_close_pct`（設成 `None` 就關掉）。

- 訊號上多一行講依據，例如
  「位置：昨收 100.00｜開盤 103.00（+3.0%）｜最低 100.60（+0.6%）→ 開高後回到昨收附近再往上」。
- 昨收不知道的那一檔判不出來，就不發。開盤價優先用券商 tick 的 open；
  沒有的話用開盤區間內收到的第一筆，更晚才開程式就只用最低點那一條判。
- 開盤、最低點離昨收幾 % 都會記進 `outcomes.csv`（`open_gap_pct`／`low_gap_pct`），
  `whynot.py` 的表也多一關「離昨收太遠」。
- **代價**：進場價通常已經比昨收高 3–6%，跳空開高、一路往上的那種會被擋掉，
  訊號會變少。停損、目標、抱兩天、進場窗口都照 v8。

### v8：停利目標依個股平常的波動

v6／v7 每一檔都是 +8%。但平常一天只動 2% 的股票要漲 8% 很難，平常動 7% 的 8% 又可能不夠。
v8 改成：**目標 = 進場價往上「這一檔近 5 日平均日振幅」%**，夾在 3%～10% 之間。

- 振幅 = (當日最高 − 當日最低) ÷ 前一日收盤，取最近 5 個交易日平均。`screener.py`
  算量比時本來就抓了這段分鐘 K，順手算，不多打 API；寫進 `watchlist.json` 的
  `avg_amplitude_pct`。算不出來（量比沒查到的那幾檔）就用昨天一天的振幅。
- 下限 3% = 停損距離（再低賺得比賠得少）；上限 10% = 一天的漲跌幅上限。
- 訊號上會寫依據，例如「目標：106.50（+5.4%，這檔近 5 日平均一天振幅 5.4%）」；
  被上下限夾住時會寫「取下限 3%」。
- 停損、抱兩天、進場窗口、前三檔排序都照 v7。**不加任何篩選條件** —— 內外盤比、
  大盤、追高 % 照記，資料夠了再決定哪個值得變成門檻。

### v6：最多抱到隔天

| | v5（當沖） | v6 |
|---|---|---|
| 停損 | 進場價 -1.5%（或結構線） | 進場價 **-3%**（或結構線，取較寬） |
| 目標 | 1.5R，貼齊當天漲停 | 進場價 **+8%**，**不**貼齊當天漲停 |
| 13:25 沒結束 | 平倉 | **📦 通知「還沒結束」，要不要留倉由你決定**；系統照樣追蹤到隔天 13:25，結果另外記 |
| 來回成本 | 0.207% | 隔天賣：0.357%（證交稅全額 0.3%） |

- 進場價通常已經比昨收高 3–6%，當天漲停只有 +10%，+8% 第一天常常到不了 ——
  這正是要抱兩天的原因。訊號上會寫「今天漲停是 X，今天到不了」。
- 隔天早上 `signals.py` 啟動時，會從**昨天的** `state.json` 接手還沒結束的部位
  （先用昨天的分鐘 K 再確認一次真的沒結束），推一則「📦 昨日留倉」，然後照常盯
  停損與目標。那幾檔當天不會再發新的買入訊號（不加碼）。**隔天一定要照常開監看。**
  沒開的話，結局仍然會由 `review.py` 用 K 棒回推，只是盤中不會通知你。
- **跳空**：隔天一開盤就在停損之下，出場價記開盤價，不記停損價 —— 那是留倉真正的
  風險，記成停損價等於把它從帳上抹掉。開在目標之上同理記開盤價。
- 到目標時推「✅ 目標」，並寫明**續抱與否由你決定**。紀錄照規則記在目標價；
  達標後在持有期內最高又走到哪，記在 `mfe_pct`，`analyse.py` 的「七、續抱分析」
  會統計有幾筆走到 +10% / +12% / +15% / +20%。
- 留倉中的那一筆**不寫進** `outcomes.csv`、不算勝率；日報上列成「留倉中（未實現）」。
  隔天收盤後的覆盤回推出結局，才寫進去（日期是訊號那一天，`exit_date` 是出場那天）。
- 已知限制：批次落選／被擋掉的候選（`candidates_outcomes.csv`）仍以當沖回推，
  目標 +8% 當天常常到不了，所以它們跟實際訊號的結果**不可以直接比較**。

出場價一律取停損／目標那個價位，不取觸發當下的報價 —— 跳空穿過去的部分另外寫在
訊息裡，不混進報酬率。這樣即時推播的數字才會和 `outcome.py` 收盤後算出來的一致，
**兩條獨立的路對不起來就表示其中一邊錯了**，驗證期兩份都留著互為對照。

訊息會明講「這不是你的實際損益」。驗證期沒有下單，把它當成自己的損益是最貴的誤會。

### 訊號後來怎麼了 —— `outcome.py`

訊號發出後程式就不再追蹤那檔，所以「後來碰到停損還是目標」從來沒被記下來。
`review.py` 現在會在收盤後自動回推：從發訊號的下一根分鐘 K 往後走，看哪一個先被碰到。

結果同時寫進當日 journal 與 `outcomes.csv`（累積檔，20 天的統計靠它）。

`outcomes.csv` 除了結局之外，也留下**發訊號當下的現場條件** —— 開盤區間高點、
均價線、量能倍數，以及兩個推導欄位：

| 欄位 | 意思 |
|---|---|
| `extension_pct` | 進場價比開盤區間高點高出幾 % —— **追高的程度** |
| `mae_pct` | 進場後整天的**最低**點離進場價幾 %（最大不利偏移） |
| `mfe_pct` | 進場後整天的**最高**點離進場價幾 %（最大有利偏移） |
| `target_after_stop` | 停損出場後，當天還是碰到目標了嗎 |
| `low_5m_pct` | 訊號後第 1~5 分鐘的最低價離進場價幾 %（≤0 表示限價掛訊號價買得到） |
| `rank` | 這檔在當天盤前選股的名次（1 = 量比最高）—— 回答「只做前 N 名會不會比較好」 |
| `daily_rsi` | 盤前算的日線 RSI(14)（Wilder）—— 只記錄 |
| `sim_move_pct` | 開盤前試撮價從第一筆到最後一筆走了幾 %（`sim_ups`／`sim_downs` 是往上／往下跳幾次，`sim_from` 是從幾點開始收到）—— 只記錄 |

### 被擋掉的候選 —— `candidates.csv`

「一天最多 5 個訊號」與「一檔一天只發一次」這兩條規則，以前是把被擋掉的訊號
**直接丟掉**：`return None`，不寫檔、不記錄。第 1、2 天都在 09:49 之前就打滿
5 個，也就是說那之後的訊號全部消失了 —— 而 20 天後要回答「上限訂多少」「被洗
掉後能不能重新進場」，靠的正是那些消失的資料。沒有紀錄，那兩題只能再測一次。

現在被擋掉的訊號照樣算完整條件，寫進 `candidates.csv`，`review.py` 收盤後用
**完全相同**的回推邏輯產出 `candidates_outcomes.csv`（多一欄 `reason`）。

| `reason` | 被什麼擋掉 |
|---|---|
| `daily_cap` | 今日訊號額度（5 個）已用完 |
| `symbol_cap` | 這檔今天已經發過訊號了 |
| `批次排序未入選` | 09:05 那一批超過 3 個，量能排序沒排進去 |
| `發出時已跌回區間`／`發出時已跌破均價線`／`發出時已漲停` | 09:05 發出當下重算，條件已經不成立 |
| `09:30 之後才突破` | 進場窗口關了才突破（只記到 10:30） |
| `量能未達門檻` | 突破、均價線都過了，量能不到 1.8 倍 |

候選**不推播、不計入風控、不進 `outcomes.csv`、不進日報** —— 策略行為一行沒改，
只是把原本丟掉的東西記下來。每檔每天最多記 3 個，且彼此至少間隔 5 分鐘，否則
突破後每個 tick 都會記一筆，記到的是同一次突破的雜訊。

日報刻意不顯示它們：每天看到「你少賺了多少」，只會讓人想把上限拆掉。
| `vwap_gap_pct` | 進場價比均價線高出幾 % |

進場價取的是「條件全部成立那一刻的現價」，不是「區間高點 + 突破緩衝」。多數時候
兩者很接近（0.5% 以內），但當一檔股票在量能或均價條件補上之前就先衝上去，進場價
可能比區間高點高出 2% 以上 —— 那是追高，停損甚至會落在區間高點**之上**，
風險結構和一般的突破完全不同。

`mae_pct` / `mfe_pct` 算的是**整天**，不是只算到出場為止 —— 問題是「如果我沒出場
會怎樣」，只看到出場那一根就答不出來。這兩個數字一次回答兩件事：**贏的那幾筆的
MAE 說明停損可以多緊而不被洗掉；輸的那幾筆的 MFE 說明停損太緊讓你錯過多少。**

2026-09-24 的光頡就是這種：進場 137.00、停損 135.00 被掃，但當天最高 144.50、
收在 140.00（剛好是目標價）。只看「停損」兩個字，看不出這一筆是被洗掉的。

**這三欄只寫進 CSV，不進每日推播。** 每天看到「其實你會贏」會慢慢侵蝕執行停損的
紀律，而停損紀律是這套系統唯一真正的保護。20 天後一次看統計才有意義。

系統目前**不擋**這種訊號（驗證期不改規則）。但這兩個欄位留著，20 天之後就答得出
「追高的那些筆，勝率是不是明顯比較差」，答得出來才知道該不該加上限。


三個刻意選擇的**保守**假設 —— 每一個都寧可低估這套系統：

| 假設 | 為什麼 |
|---|---|
| 同一根 K 同時觸及停損與目標 → **判停損** | 分鐘 K 只有開高低收，看不出那一分鐘內誰先到。往壞處算 |
| 成交價 = 訊號上的價位，**不計滑價** | 真實交易會有滑價，實際成績只會比這裡差 |
| **13:25** 平倉，不是 13:30 | 尾盤集合競價那五分鐘不保證出得掉（v6 留倉的那一筆第一天看到 13:30：你沒走，尾盤那一下也算） |

**回推從「完全在訊號之後」的那一根 K 棒開始。** K 棒時間戳是該分鐘的結束時間，
所以「label 大於訊號時間」的第一根，涵蓋的其實是訊號發出**前**的那幾十秒。

這一點曾經被當成「略偏保守」而留著，那是錯的：突破訊號依定義發在股價剛越過開盤
區間高點的那一刻，而停損就設在區間高點下方一點 —— 那一根裡訊號發出前的成交全都
還在區間高點之下，低點幾乎必然掃到停損。2026-09-24 五個訊號有四個被判成「第一根
就停損」，而其中的合晶當天實際走到目標並收在更高的價位。**那不是市場的結果，是尺
量錯了。**

代價是訊號後最多 60 秒看不到。那段空白對停損與目標一視同仁，不偏向任何一邊，而且
盤中的即時追蹤看的是 tick，正好補上這一段。

**勝率的定義是「扣掉來回成本後為正」** —— 毛賺但被成本吃光的那一筆不算贏。

跨日稽核的提問固定用這三個：
1. 這四週我最常違反哪一條規則？
2. 我賺錢的交易和虧錢的交易，進場理由有什麼系統性差異？
3. 如果只保留一種訊號型態，數據上該保留哪一種？

> 睡過頭、程式重開、09:15 之後才啟動 `signals.py` 都沒關係：
> 它會用分鐘 K 把開盤區間補算回來（`SIGNAL.backfill_opening_range`）。
> 補不到的那幾檔會明確告訴你「今天不會發訊號」，而不是安靜地整天沉默。

## 即時判定與收盤回推衝突時，以 tick 為準

`bars_after()` 刻意丟掉訊號後的頭 60 秒 —— 那一根 K 棒涵蓋訊號發出**前**的時間，
留著會製造假停損（2026-09-24 五個訊號誤判四個）。代價是走得快的那幾筆就結束在
那個空窗裡。

2026-09-29 允強：09:32:13 發訊號、**09:32:25（12 秒後）到目標**。即時推播說
+1.57R，收盤覆盤說 −1.00R —— 分鐘 K 看不到那 12 秒，只看到後來跌回去碰停損。
同一筆交易兩個答案，差 2.57R。

原本 `outcome.py` 的註解寫著「LiveTracker 看 tick，正好補上這一段」。**那句話在
程式裡不成立**：即時結果只活在那則 Telegram 訊息裡，沒人寫下來，`outcome.py`
從來沒看過它。

現在 `LiveTracker` 判定完會把結果寫回 `state.json` 的那一筆訊號
（`live_result` / `live_exit` / `live_at`），`review.py` 讀回去交給 `resolve()`，
**有 tick 判定就以它為準**，沒有才用分鐘 K。tick 是實際成交，分鐘 K 是事後摘要。

整天的極值（`mae_pct` / `mfe_pct` / `low_5m_pct`）仍然一律由 K 棒算；K 棒抓不到
時留空，不猜。`bars` 欄為 0 表示這一筆是 tick 判定的。

## 測試不會推到你手機

2026-09-29：使用者跑一次 `python test_daytrade.py`，手機收到 5 則「今日停手」，
其中一則寫著「原因：測試」。`RiskGate._close()` 直接呼叫 `notify()`，而使用者的
機器上 `.env` 有金鑰、`requests` 也裝了 —— 測試就真的把訊息推出去。
CI 兩樣都沒有，所以這個洞在 CI 裡永遠不會露出來。

`config.push_enabled()` 現在是唯一的出口判斷，兩層保險：

- 環境變數 `DAYTRADE_NO_PUSH=1`（`dryrun.py` 與 `test_daytrade.py` 都會設）
- `unittest` / `pytest` 只要在 `sys.modules` 裡就一律不推 —— 就算未來新增的測試檔
  忘了設環境變數也漏不出去

測試裡有一條 `test_push_is_disabled_while_these_tests_run`：保險絲斷掉的話，
整份測試會失敗，而不是等你手機響了才發現。

## 參數紅線（`config.py`）

```
max_signals_per_day      5      一天最多 5 個訊號
max_trades_per_day       4      一天最多 4 筆
max_daily_loss           12000  虧到這裡，系統當日不再發訊號
max_consecutive_losses   3      連三敗停手
per_trade_risk           3000   單筆風險 → 反推張數
```

**這些數字只能在開盤前改。** 盤中想調鬆 = 系統失效的瞬間。
建議直接 `chmod 444 config.py`，要改就得有意識地解鎖。

`config.validate()` 在三支程式啟動時都會跑，參數互相矛盾會直接擋下來不讓你開盤。
它擋的不只是打錯字 —— 例如 `per_trade_risk × max_trades_per_day < max_daily_loss`
時，日虧上限永遠不會被觸發，那條紅線形同虛設，它會講出來。

**停損與目標價會進位到台股合法檔位**（<10 元 0.01／<50 0.05／<100 0.1／<500 0.5…），
兩者都往有利於風控的方向進位：停損取較緊的那一檔（實際風險不超過
`stop_loss_pct`），目標取較遠的那一檔（成交時 R 倍數不低於 `reward_risk`）。
算出 99.48 這種價位是沒有意義的 —— 你照著下單會被退單或自動修價，
真正的停損位置就不是你以為的那個了。

**目標價也不可以超過當日漲停。** 2026-09-24 的嘉晶：昨收 145.5、漲停 160.0，而系統
發了 161.00 的目標。那一筆被判成「收盤平倉」，不是因為它沒走到目標，是因為**那個
價位當天不存在** —— 它漲停鎖死在 160.0。現在目標會貼齊漲停，訊號上寫明賺賠比因此
縮水到多少（不假裝還是 2.5R）；現價已經漲停鎖死則不發訊號，那個價位你買不到，
買到也沒有上檔空間。

這跟檔位進位是同一類問題：不是參數調得好不好，是這個數字在現實中下不出去。

## 上線順序（不要跳）

1. **第 1 個月**：`SIMULATION=1`，只跑 screener + signals，不下單。
   看訊號品質：一天發幾個？假突破比例多高？
2. **第 2 個月**：真錢，但每筆 1 張。目的是測「你會不會照停損走」，不是賺錢。
   **切到 `SIMULATION=0` 的第一天，第一件事是確認損益查得到** ——
   查不到的話風控閘門會直接關閘停手（見下方「風控的煞車」）。
3. **第 3 個月**：把 `journal/` 三個月資料丟進去算真實勝率與賺賠比。
   **期望值跨不過來回成本 0.2% 就停掉，不要加碼救它。**
4. 之後才談要不要擴大部位。

## 風控的煞車

日虧上限與連敗停手兩條線，都建立在「查得到當日已實現損益」之上。
`realized_pnl_rows_today()` 查不到時回傳 **None（未知）而不是 0**，兩者差很多：

- 真錢模式（`SIMULATION=0`）查不到 → **直接關閘**。
  沒有煞車就不上路；請檢查電子憑證與帳號權限。
- 模擬模式查不到 → 以 0 計算並留下警告。
  模擬帳本來就沒有損益可查，硬停手會讓第一個月完全跑不出訊號品質數據。

這個取捨寫在 `RISK.halt_when_pnl_unknown`。把它關掉之前先想清楚：
你關掉的是「虧到上限會自動停手」這件事本身。

## 已知限制

- ORB 在跳空開高的日子容易假突破，這是策略本身的弱點，不是 bug
- 分鐘 K 的 `ts` 是「台北牆上時間編成 UTC」，`_bar_time()` 必須以 UTC 解讀。
  用本機時區解會在台灣的電腦上整整差 8 小時（09:00 的 K 棒變 17:00），
  開盤區間永遠補算不到。CI 會同時以 UTC 與 Asia/Taipei 跑測試守住這件事
- `volume_surge` 用 tick 累計量估算。取樣長度不足時回傳 0（等於不發訊號）而非硬算，
  但它終究是估算，不是交易所的分時量
- 量比（`volume_ratio`）只對振幅前 60 名計算，其餘以 1.0 計 ——
  Shioaji 有流量上限，全市場每檔打一次 kbars 會被停用一分鐘
- `day_trade` 旗標為 `OnlyBuy`（只能先買後賣）的標的**會被納入**，因為 v1 只做多。
  要做空時它們就不能收 —— `is_day_tradable()` 依 `allow_short` 自動切換。
  認不出來的旗標值一律當成不可當沖（寧可少看幾檔）；實際值分佈用 `preflight.py` 確認
- 先賣後買（`allow_short`）**沒有實作**：`evaluate()` 只有多方分支。
  在 `config.py` 打開它會被 `validate()` 擋下來，而不是讓你誤以為系統在看空單
- Shioaji 每 24 小時需重新登入（`ensure_session()` 每 30 秒檢查，滿 20 小時主動重登）
- 風控閘門只看**已實現**損益。手上還抱著的未實現虧損它看不到
- `require_above_vwap` 在拿不到均價線時**不發訊號**（而不是把規則跳過）。
  某檔整天都拿不到 `avg_price` 的話，它今天就不會有訊號，log 會講一次
- 沒有訊號時，風控每 `RISK.poll_interval_sec`（預設 5 分鐘）才主動查一次帳務。
  縮短它會撞到 Shioaji 流量上限、被停用一分鐘 —— 那一分鐘你連行情都收不到
- 訊號數與紀律稽核都假設 `max_signals_per_symbol = 1`（一檔 = 一筆來回）。
  改大這個值，`review.py` 的「交易檔數」判定就要跟著改

## 檔案

| 檔案 | 角色 |
|------|------|
| `config.py` | 所有參數 + `validate()` + 檔位進位 + 成本模型 |

`state.json`、`watchlist.json` 與 `journal/*.md` **不進版控**：
那是你的帳務與持股紀錄。要給 Claude 做跨日稽核時，直接把本機的 `journal/` 丟給它。
